# Архитектурный документ проекта "Date Invitation"

## 1. Обзор проекта

**Date Invitation** — это веб-приложение для создания красивых персональных приглашений на свидание. Администратор создаёт приглашение через админ-панель, получает уникальную ссылку и отправляет её партнёру. Получатель проходит пошаговый wizard (приветствие → выбор даты → выбор места → прощание), а ответ сохраняется в базе данных для последующего анализа.

### Ключевые ценности продукта
- **Эмоциональность** — интерфейс должен вызывать улыбку, нежность и романтику.
- **Простота** — получатель не должен думать, только нажимать большие кнопки.
- **Персонализация** — каждый элемент приглашения настраивается в админке.
- **Аналитика** — администратор видит, кто открыл ссылку и что выбрал.

### 3.2 Clean Architecture (Backend)

Backend построен по принципам clean architecture с разделением на слои:

```
src/
├── modules/                    # Бизнес-модули (по фичам)
│   ├── auth/                   # Аутентификация
│   │   ├── auth.module.ts
│   │   ├── auth.controller.ts  # HTTP-слой
│   │   ├── auth.service.ts     # Use-case слой
│   │   ├── strategies/         # JWT стратегии
│   │   └── dto/                # DTO (входные данные)
│   ├── invitations/            # Приглашения
│   ├── responses/              # Ответы
│   └── analytics/              # Аналитика
├── prisma/                     # Prisma schema + миграции
├── common/                     # Общие утилиты, декораторы, фильтры
└── main.ts                     # Точка входа
```

**Принципы:**
- **Модульность** — каждый модуль самодостаточен (контроллер + сервис + DTO).
- **Разделение ответственности** — контроллеры обрабатывают HTTP, сервисы — бизнес-логику.
- **DTO валидация** — все входные данные проходят через class-validator.
- **Инверсия зависимостей** — через DI-контейнер NestJS.

### 3.3 Модель данных (Prisma)

```
┌────────────┐     ┌──────────────────┐     ┌─────────────┐
│   User     │     │   Invitation     │     │  Invitation │
│────────────│     │──────────────────│     │    Step     │
│ id         │     │ id               │     │─────────────│
│ email      │     │ title            │     │ id          │
│ password   │     │ headline         │     │ invitationId│
│ name       │     │ greetingText     │     │ type        │
│ createdAt  │     │ gifUrl           │     │ label       │
│            │     │ token            │     │ order       │
│            │     │ status           │     │ createdAt   │
│            │     │ views            │     └─────────────┘
│            │     │ createdAt        │
│            │     │ updatedAt        │
│            │     └──────────────────┘
│            │              │
└────────────┘              │ 1:N
                            ▼
                    ┌─────────────┐
                    │   Answer    │
                    │─────────────│
                    │ id          │
                    │ invitationId│
                    │ dateStepId  │
                    │ placeStepId │
                    │ createdAt   │
                    └─────────────┘
```

**Обоснование модели:**
- **InvitationStep** — гибкая модель шагов. Тип (`DATE` | `PLACE`) определяет, к какому экрану относится вариант. Это позволяет добавлять произвольное количество дат и мест без изменения схемы.
- **Answer** — хранит выбранные дату и место. Связь с шагами через внешние ключи.
- **views** — счётчик просмотров, инкрементируется при открытии ссылки.

## 4. API Design

### 4.1 Аутентификация

| Метод | Endpoint | Описание |
|-------|----------|----------|
| POST | `/auth/login` | Вход, возвращает JWT |
| GET | `/auth/me` | Текущий пользователь (protected) |

### 4.2 Приглашения (админ)

| Метод | Endpoint | Описание |
|-------|----------|----------|
| GET | `/invitations` | Список приглашений (protected) |
| POST | `/invitations` | Создать приглашение (protected) |
| GET | `/invitations/:id` | Детали приглашения (protected) |
| PATCH | `/invitations/:id` | Обновить приглашение (protected) |
| DELETE | `/invitations/:id` | Удалить приглашение (protected) |

### 4.3 Публичные (получатель)

| Метод | Endpoint | Описание |
|-------|----------|----------|
| GET | `/invite/:token` | Получить приглашение по токену (инкрементирует views) |
| POST | `/invite/:token/answer` | Отправить ответ |

### 4.4 Аналитика

| Метод | Endpoint | Описание |
|-------|----------|----------|
| GET | `/analytics/:id` | Статистика по приглашению (protected) |

### 5.2 Управление состоянием

- **auth.store** — JWT токен, пользователь, состояние авторизации.
- **invite.store** — текущее приглашение, выбранные шаги, прогресс wizard.

### 5.3 Сохранение прогресса

Прогресс wizard сохраняется в `localStorage` по ключу `invite-progress-{token}`. При обновлении страницы пользователь возвращается к текущему шагу.

## 6. UX/UI Design

### 6.1 Дизайн-система

- **Цвета**: белый фон, пастельные акценты (розовый `#FFB6C1`, персиковый `#FFDAB9`, лавандовый `#E6E6FA`).

- Большие кнопки (min-height 56px).

## 7. Безопасность

- **JWT** — подписанные токены, срок действия 24ч.
- **bcrypt** — хеширование паролей.
- **CORS** — ограничен origin frontend.

## 10. Комментарии к ключевым решениям

1. **Почему NestJS, а не Express?** — Модульная структура, DI, декораторы, встроенная валидация. Идеально для clean architecture.

2. **Почему Prisma?** — Типобезопасность, автогенерация типов, простые миграции. Ускоряет разработку.

3. **Почему InvitationStep, а не отдельные таблицы для дат и мест?** — Единая гибкая модель. Добавление нового типа шага не требует миграции.

4. **Почему localStorage для прогресса?** — Простота, не требует серверной логики. Получатель не авторизован.

5. **Почему Tailwind?** — Быстрая разработка, консистентность, mobile-first из коробки.

6. **Почему views как счётчик, а не отдельная таблица?** — Для MVP достаточно. При необходимости можно вынести в отдельную таблицу для детальной аналитики.
